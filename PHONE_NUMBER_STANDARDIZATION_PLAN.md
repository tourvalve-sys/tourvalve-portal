# Standardize phone number format across booking (frontend → Travelport / Atlas → DB)

## Context
Today, the booking flow's contact phone number is a single free-text input (`frontend/app/booking/page.tsx`) with only a "non-empty" check — no format validation, no country-code handling, no normalization. That same raw string is sent unmodified to whichever provider handles the booking (Travelport or Atlas/AtripTech), and neither backend integration does any parsing or reformatting either. This plan defines a standardized, user-friendly input format for the frontend, a canonical internal format, and the per-provider conversion needed at submission time — plus what format to use if the phone number is ever persisted to the database (it currently is not, for bookings).

This is a **documentation-only deliverable** — no code has been changed as part of this plan.

## Investigation findings

### Frontend (`frontend/app/booking/page.tsx`, `frontend/lib/api.ts`)
- Single shared "contact phone" for the whole booking (not per-passenger): `contactPhone` state ([booking/page.tsx:398](frontend/app/booking/page.tsx#L398)), plain `<input placeholder="Phone Number">` with no `type="tel"`, no pattern, no masking ([booking/page.tsx:1464-1469](frontend/app/booking/page.tsx#L1464-L1469)).
- Validation today is presence-only: `if (!contactEmail || !contactPhone) { setError("Contact email and phone are required."); return; }` ([booking/page.tsx:901-904](frontend/app/booking/page.tsx#L901-L904)). Only `.trim()` is applied before submit (line 949).
- Both providers share **one payload type and one call site**: `AirBookingPayload.contactPhone: string` ([lib/api.ts:332](frontend/lib/api.ts#L332)), sent by `bookFlight()` (Travelport, → `POST /api/air-booking`) and `bookAtlasFlight()` (Atlas, → `POST /api/atlas/booking`) — both defined at lib/api.ts:1068-1088. The caller already branches on provider via `selectedFlight.providerCode` right before calling one or the other ([booking/page.tsx:929](frontend/app/booking/page.tsx#L929)) — so there's already a single, provider-aware choke point to hook into.
- No phone library, no country-code selector, and no validation/formatting utility exists anywhere in the frontend today (confirmed via full-repo search). The agent-registration page (`frontend/app/register/page.tsx:84-90`) has a similar free-text phone field with a placeholder hinting at Malaysia's `+60` format, but no enforcement either — same pattern, separate flow, not in scope for this change but worth flagging as a natural follow-up for consistency.

### Travelport (`backend/TourValve.Api/Controllers/AirBookingController.cs`)
- Only one place writes phone into the outbound XML: `BuildReservationRequest`, which emits `<com:PhoneNumber Number="{Escape(request.ContactPhone)}" />` per traveler ([AirBookingController.cs:354](backend/TourValve.Api/Controllers/AirBookingController.cs#L354)) — a single flat `Number` string attribute (Universal API `common_v52_0` schema). No `CountryCode`/`AreaCode`/`Extension`/`Type` attributes are populated; `Escape()` only does XML-entity escaping, not format conversion.
- **Verified against Travelport's official Universal API docs and tutorial samples** (support.travelport.com + Travelport's public GitHub tutorials — see Sources): the `PhoneNumber` element's documented/intended usage is a **split structure**, not one flat string:
  - `CountryCode` — the international dialing code (e.g. `"1"`, `"60"`, `"86"`), digits only, no `+`.
  - `AreaCode` — required for NANP (US/Canada) numbers specifically, 3 digits. Not applicable/required for most other countries (confirmed: *"@AreaCode is required for domestic phone numbers [NANP] and must be 3 digits"*).
  - `Number` — the remaining local subscriber number (7 digits for NANP; the full national number for everywhere else).
  - Optional: `Type` (`Business`/`Mobile`/`Home`/`Fax`/`Other`/etc.), `Location`, `Extension`, `Key`.
  - Real tutorial examples: `<PhoneNumber CountryCode="1" AreaCode="212" Number="555-1212" Type="Home" Location="MON" />`, `<PhoneNumber CountryCode="1" AreaCode="617" Number="4892000" />`.
  - Also documented: *"Some ACH carriers require the area code to be separate in @AreaCode. Other carriers will parse the area code as part of the string in @Number"* — i.e. some suppliers specifically reject a phone number that isn't split, reinforcing that the current single-`Number`-attribute implementation is a simplification that happens to have worked so far, not a documented-correct usage.
  - **Conclusion: the current backend implementation should be corrected, not just format-converted.** Instead of E.164 → digits-only into one `Number` attribute (the original, unverified assumption), it should populate `CountryCode` = the calling code, and `Number` = the national significant number — with `AreaCode` additionally split out (first 3 digits of the national number) only when `CountryCode == "1"` (NANP).

### Atlas / AtripTech (`backend/TourValve.Infrastructure/Atlas/Models/AtlasOrderContact.cs`, `AtlasBookingController.cs`)
- `AtlasOrderContact.Mobile` is a plain `string` with an existing code comment: `// Prefer E.164 with country code when possible.` ([AtlasOrderContact.cs:13](backend/TourValve.Infrastructure/Atlas/Models/AtlasOrderContact.cs#L13)).
- `AtlasBookingController.BuildOrderRequest` assigns `Mobile = request.ContactPhone` verbatim ([AtlasBookingController.cs:567](backend/TourValve.Api/Controllers/AtlasBookingController.cs#L567)) — no conversion happens today.
- **This code comment turns out to be wrong.** AtripTech (the vendor behind our "Atlas" integration — confirmed by their own docs portal at `resources.atriptech.com`, which uses "Atlas" as the product name) publishes an official API reference for their Create Order endpoint (`resources.atriptech.com/api-document/api-reference/booking-apis/create-order.md`) which explicitly documents the `contact.mobile` field format as:
  > *"please follow this format: `XXXX(digital country code)-XXXXXXXX(phone number)`, here're the examples: `0001-87291810`, `0086-13928109091`, `0971-19201998`"*
  - That is: a **4-digit, zero-padded country calling code**, a hyphen, then the national number — **not E.164** (no `+`, and the country code is zero-padded to 4 digits rather than used at its natural 1-3 digit length). E.g. for Malaysia (`+60`) this would be `0060-1XXXXXXXX`.
  - The field is documented as an optional/nullable string with no additional regex or length constraint beyond the format description.
  - **Action: fix the misleading code comment and implement the actual documented conversion** (E.164 → 4-digit zero-padded country code + hyphen + national number) in `AtlasBookingController.BuildOrderRequest`, rather than passing E.164 through as previously assumed.

### Database storage
- **The `Booking` entity has no phone column at all** ([backend/TourValve.Domain/Booking.cs](backend/TourValve.Domain/Booking.cs) — confirmed, no `ContactPhone`/`Phone`/`Mobile` field). Contact phone is never persisted for a booking; it's purely a pass-through value forwarded to the provider at booking time. For post-booking display (PDFs), the phone is **re-extracted from Travelport's own XML response** at render time ([BookingItineraryPdfBuilder.cs:507-538](backend/TourValve.Api/Pdf/BookingItineraryPdfBuilder.cs#L507-L538)), not read back from our DB.
- Phone numbers **are** persisted elsewhere, unrelated to bookings: `Agent.PhoneNumber` and `RegistrationApprovalRequest.PhoneNumber`, both plain unconstrained Postgres `text` columns (no length limit, no format check) — see migration `20260326113000_AddAccessApprovalRequests.cs`.
- Since bookings don't currently store a phone number, no DB schema change is required by this plan. The recommendation below is for *if/when* one is added later (either for `Booking` or for normalizing the existing `Agent`/`RegistrationApprovalRequest` columns) — noted so the format decision is made consciously rather than by accident.

## Recommended standardized format

**User-facing input (frontend):** Country selector (dropdown of country dial codes, defaulting to Malaysia `+60` to match the existing register-page convention) paired with a text field that live-formats as the user types, using the `libphonenumber-js` library (small, dependency-free, well-maintained; provides `AsYouType` for live formatting and `parsePhoneNumberFromString`/`isValidPhoneNumber` for validation). This was chosen over a fixed-single-country field or unformatted free text specifically to support international travelers cleanly.

**Canonical internal format:** E.164 (e.g. `+60123456789`) — the value produced by `libphonenumber-js` once parsed against the selected country. Note: the existing `AtlasOrderContact.Mobile` code comment claims Atlas "prefers E.164," but that turned out to be incorrect (see below) — E.164 is still the right *canonical/wire* format here on its own merits:
- Unambiguous and self-contained (includes country code, no locale-dependent punctuation), making it the right choice if/when it's ever persisted to the DB.
- A single, uniform value the frontend sends to the backend for `AirBookingPayload.contactPhone` regardless of which provider will receive the booking — keeping the wire format consistent, and pushing each vendor's idiosyncratic formatting requirement to the boundary closest to that vendor (the backend controllers that already build each provider's request).

**Per-provider conversion at submission time (backend, not frontend) — corrected after checking both vendors' official docs:**
- **Atlas/AtripTech** (`AtlasBookingController.BuildOrderRequest`): convert E.164 → `{4-digit zero-padded calling code}-{national number}` (e.g. `+60123456789` → `0060-123456789`), matching AtripTech's documented `create-order` API format exactly. Also correct the misleading `// Prefer E.164` comment on `AtlasOrderContact.Mobile`.
- **Travelport** (`AirBookingController.BuildReservationRequest`): stop writing everything into a single `Number` attribute. Instead populate `CountryCode` (the calling code, e.g. `"60"`, `"1"`, `"86"`, digits only) and `Number` (the national significant number); additionally split out `AreaCode` (first 3 digits of the national number) only when `CountryCode == "1"` (NANP — the only region where Travelport's docs say `AreaCode` is required/expected as a separate attribute). This matches Travelport's own Universal API tutorial examples (e.g. `<PhoneNumber CountryCode="1" AreaCode="617" Number="4892000" />`).

Sources checked: Travelport Universal API support docs ([Booking Traveler Information](https://support.travelport.com/webhelp/uapi/Content/Booking/UniversalRecord/Booking_Traveler_Information.htm), [Creating Air Bookings](https://support.travelport.com/webhelp/uapi/Content/Air/Air_Booking/Create_Air_Booking/Creating_Air_Bookings.htm)) and Travelport's public tutorial repos (`Travelport/travelport-uapi-tutorial*` on GitHub) for the `PhoneNumber`/`CountryCode`/`AreaCode`/`Number` structure; AtripTech's own API reference docs (`resources.atriptech.com/api-document/api-reference/booking-apis/create-order.md`) for the `contact.mobile` format.

**Database (if/when persisted):** Store E.164. No schema change is required right now since `Booking` has no phone column today; this is guidance for whenever that changes (either a new `Booking.ContactPhone` column, or normalizing the existing free-text `Agent.PhoneNumber` / `RegistrationApprovalRequest.PhoneNumber` columns), so the format is a deliberate choice rather than whatever falls out of ad hoc frontend input.

## Implementation outline (as implemented)
1. Added `libphonenumber-js` (`^1.13.9`) to `frontend/package.json` via `npm install`.
2. New `frontend/lib/phone.ts`: `getPhoneCountryOptions()` (country list with `Intl.DisplayNames` labels + dial codes), `formatPhoneAsYouType(value, country)`, `isValidPhone(value, country)`, `toE164(value, country)`.
3. `frontend/app/booking/page.tsx`: added a `contactPhoneCountry` state (default `"MY"`) and a country-code `<select>` next to the phone input; the phone `<input>` (now `type="tel"`) live-formats via `formatPhoneAsYouType` on every keystroke. `handleBooking` now validates with `isValidPhone` and converts to E.164 via `toE164()` right before calling `submitBooking(...)`, rejecting the booking with an inline error if the number doesn't parse — same E.164 value sent regardless of provider.
4. Backend: added the `libphonenumber-csharp` NuGet package (v9.0.35, namespace `PhoneNumbers`) to `TourValve.Application`, and a new `TourValve.Application/Common/PhoneNumberFormatter.cs` with `IsValidE164`, `ToAtripTechMobile` (→ `{4-digit zero-padded calling code}-{national number}`), and `ToTravelportPhoneParts` (→ `CountryCode`/`AreaCode`(NANP only)/`Number`).
   - `AtlasBookingController.BuildOrderRequest`: `Mobile = PhoneNumberFormatter.ToAtripTechMobile(request.ContactPhone) ?? request.ContactPhone`. Fixed the incorrect `// Prefer E.164` comment on `AtlasOrderContact.Mobile`.
   - `AirBookingController.BuildReservationRequest`: replaced the flat `<com:PhoneNumber Number="...">` with a new `BuildPhoneNumberXml` helper that emits `CountryCode`/`AreaCode`/`Number` attributes via `PhoneNumberFormatter.ToTravelportPhoneParts` (falling back to the old flat `Number`-only form if parsing fails, so a booking is never hard-blocked by this alone).
   - Added `PhoneNumberFormatter.IsValidE164(request.ContactPhone)` checks in both `AirBookingController.Book` and `AtlasBookingController.Book` entry points (defense in depth, on top of the frontend validation).
5. Not done (flagged as optional/out of scope, per the original plan): `frontend/app/register/page.tsx`'s phone field was left as free text — not touched.

### Post-implementation fix: country-select layout overflow
After shipping, the country `<select>` + phone `<input>` row in `frontend/app/booking/page.tsx` was found to overflow its grid cell in the browser — the `<select>` had no width constraint, so a long country name (e.g. "Malaysia (+60)") sized the select to its content, and because neither the flex container nor its children had `min-w-0`, the row grew wider than its grid column instead of shrinking, pushing the phone input off the edge of the panel. Fixed by giving the select a fixed `w-32 shrink-0 truncate` (so long labels ellipsis instead of expanding) and adding `min-w-0` to both the flex container and the phone input so it can shrink properly within its grid cell.
