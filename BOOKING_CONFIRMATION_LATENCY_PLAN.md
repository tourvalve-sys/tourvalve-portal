# Minimize synchronous work during booking confirmation; defer ticketing/order-status checks to the existing background scheduler

## Context
Confirming a booking is slow today because both providers' ticketing calls block the booking request while retrying/polling for ticket confirmation (Atlas: up to ~3 minutes polling `queryOrderDetails.do` after payment; Travelport: nested retry loops re-fetching the Universal Record and verifying ticket documents). The user wants "confirm booking" to do the minimum required and immediately return, deferring the wait to a background process — with a clear rule for telling immediate real errors apart from the normal "provider just needs more time" case. This is a **documentation-only deliverable** — no code has been changed as part of this plan.

**Agreed design, in the user's own terms:**
- **Atlas**: the synchronous flow ends at payment (`order.do` already happened earlier; `pay.do` runs once). No synchronous polling for ticket evidence.
- **Travelport**: still attempt ticket issuance once, synchronously. If that single attempt hits a genuine immediate error, say so right away. If it doesn't (the far more common case — the provider just needs time), don't retry inline.
- **Both providers, same rule**: distinguish "no error, provider just needs time" (→ respond immediately: "confirmed, ticketing pending, check Bookings") from "a real error happened" (→ respond immediately: "confirmed [reservation/order still stands], but ticketing hit an error: <reason>"). Either way, the underlying reservation/order is never in doubt if it already succeeded — only the ticketing outcome is uncertain/delayed.
- A background scheduler keeps checking status/documents later and updates the booking, which is what the Bookings page reflects.

## Key finding: the background scheduler already exists — this is an extension, not new infrastructure
`backend/TourValve.Api/Services/AirTicketingWorker.cs` is a `BackgroundService` that already runs every 1 minute, calls `AirTicketingWorkflowService.GetDueBookingIdsAsync(...)`, and re-invokes `IssueAsync(..., backgroundTriggered: true, ...)` for each due booking. `GetDueBookingIdsAsync` (`AirTicketingWorkflowService.cs:636-655`) already selects bookings whose `AirTicketingStatus` is `SCHEDULED`, `AWAITING_EVIDENCE`, or a specific `FAILED`-but-recoverable case, gated by `AirTicketingDate <= today`. **This means the "scheduler" the user asked for already exists and runs continuously — the work here is making both providers land in `AWAITING_EVIDENCE` quickly (instead of blocking synchronously), and making that background loop able to resolve Atlas bookings too (today it can only meaningfully resolve Travelport bookings).**

## Provider-by-provider findings (confirmed by direct code read)

### Atlas — where the synchronous wait happens
`backend/TourValve.Infrastructure/Atlas/AtlasTicketingService.cs`, `IssueAsync` (lines 22-51):
1. `PayAsync(...)` — submits payment (line 32).
2. `QueryUntilTicketedAsync(orderNo, ...)` (lines 40, 126-178) — polls `queryOrderDetails.do` up to **12 times**, 5s initial delay growing ×1.5 (capped at 20s) — up to **~3 minutes** of synchronous waiting.
3. `AtlasTicketingStrategy.IssueAsync` (lines 15-27) then **throws** `InvalidOperationException` if `TicketNumbers.Count == 0` even after all that polling — today, Atlas has no non-throwing "pending" outcome at all; it either fully succeeds or fails.

### Travelport — where the synchronous wait happens
`backend/TourValve.Infrastructure/Travelport/Air/BookingTicketingService.cs`:
- `RetrieveRetryCount = 4`, `RetrieveRetryDelay = 2s` (lines 10-11).
- `IssueAsync` (lines 33-93): posts `AirTicketingReq`, then retries retrieving the Universal Record up to 4× (lines 56-71) if no ticket numbers came back.
- `VerifyIssuedDocumentsAsync` (lines 503-544): a **second**, separate up-to-4× retry loop verifying real ticket documents.
- Unlike Atlas, Travelport's outer workflow (`AirTicketingWorkflowService.IssueAsync`, lines ~279-323) **already has** a non-throwing "AWAITING_EVIDENCE" outcome for "no evidence yet, not necessarily an error" (via `BookingTicketingService.ExtractTicketingFailureDetail` + the `IsTicketingEvidencePending`/`EvidencePendingWindow` classifier already hardened in the ticketing-error-transparency work) — this plan mostly needs to make that outer classification get *reached faster*, by trimming the internal retry loops that currently delay it.
- On resumption, `AirTicketingWorkflowService.IssueAsync` (lines 164-175) already special-cases `AirTicketingStatus == AWAITING_EVIDENCE` by routing to `RefreshTicketEvidenceAsync` instead of re-running the whole ticketing call — this is exactly the "check status later without redoing the transactional step" pattern already built for Travelport; Atlas needs the equivalent.

## Recommended design

1. **Travelport (`BookingTicketingService.IssueAsync` / `VerifyIssuedDocumentsAsync`)**: trim both internal retry loops down to a single attempt (or remove the loop, keep one check) so the method returns quickly whether or not ticket numbers are present yet. Missing evidence stops being something this inner service retries for — it becomes the outer workflow's job to decide "pending" vs "failed," same as it already does today, just reached in ~1 call instead of ~9 calls' worth of retries.
2. **Travelport (`AirTicketingWorkflowService.IssueAsync`)**: verify the existing "no ticket numbers → `AWAITING_EVIDENCE` unless classified as a permanent failure" branch remains the default now that the inner retries are gone (it should — this logic doesn't change, it just gets reached sooner). A genuine immediate error (e.g. Travelport rejects the `AirTicketingReq` itself, or the failure message matches a known-permanent pattern like "TICKETING NOT ALLOWED"/IATA-type errors) still throws, which the controller already turns into "reservation confirmed, but ticket purchase failed: <reason>" per the ticketing-error-transparency work.
3. **Atlas (`AtlasTicketingService.cs`)**: split `IssueAsync` into two distinct operations:
   - `PayAsync(...)` — runs once, synchronously, during booking confirmation.
   - A single (non-looping) status check right after payment — if tickets are already present (can happen), mark `ISSUED` immediately; if not, that's the expected/default outcome, not an error.
   - A **separate** "check status only" method (no `PayAsync` call) for the background worker to call on later ticks, so payment is never resubmitted.
4. **Atlas (`AtlasTicketingStrategy.cs`)**: stop throwing when `TicketNumbers.Count == 0` on the first attempt — return a "pending" result instead, so the outer `AirTicketingWorkflowService` can classify it as `AWAITING_EVIDENCE` (mirroring Travelport) rather than a hard failure. Genuine Atlas API errors (`AtlasApiException` from a real HTTP/payment-decline/validation failure) still propagate and get classified as `FAILED`.
5. **`AirTicketingWorkflowService.IssueAsync`'s Atlas branch**: add the same "already `AWAITING_EVIDENCE` → just re-check status, don't re-pay" dispatch Travelport already has (mirroring `RefreshTicketEvidenceAsync`), using `AirTicketingPaymentStatus` to confirm payment was already submitted before allowing a status-only recheck.
6. **Confirm `AirTicketingDate` gets set for Atlas bookings** the same way it already does for Travelport bookings, so the existing `GetDueBookingIdsAsync`/`AirTicketingWorker` (already running every minute — no new scheduler needed) naturally picks up pending Atlas bookings without any change to the worker itself.
7. **API response shape**: this is the direct precondition for the already-written `TICKETING_ERROR_TRANSPARENCY_PLAN.md` (canonical outcome states `TICKETED` / `RESERVED_PENDING_TICKET` / `RESERVED_TICKETING_FAILED` and the shared `BookingOutcomeBanner`). Once this plan ships, "pending" becomes the dominant immediate outcome for both providers instead of a rare edge case — making that transparency work directly load-bearing rather than optional polish. The two plans should be implemented together: this plan makes "confirmed, ticketing pending" the normal fast response; that plan makes sure the confirmation page and Bookings list say so clearly (and say "ticketing error" clearly on the real-error path) instead of implying success either way.

## Implementation notes (as built)
1. **`BookingTicketingService.cs` (Travelport)**: both internal retry loops (`IssueAsync`'s post-ticketing record-retrieve retry, and `VerifyIssuedDocumentsAsync`'s document-verify retry) were trimmed to a single attempt each; `RetrieveRetryCount`/`RetrieveRetryDelay` were removed entirely since nothing retries anymore. `VerifyIssuedDocumentsAsync` no longer takes a `Booking` parameter (it no longer needs to re-fetch the record mid-loop).
2. **`AtlasTicketingService.cs`**: `IssueAsync` now does `PayAsync` + a single `queryOrderDetails.do` check (previously up to 12 polling attempts over ~3 minutes) via a new private `QueryOrderDetailsOnceAsync` helper. A new public `CheckStatusAsync` method does the single status check **without** calling `PayAsync`, for the background worker to call on later ticks.
3. **`IAirTicketingStrategy.cs`**: added `CheckPendingIssueAsync(Booking, CancellationToken)` to the interface, for re-checking a pending issuance without repeating the transactional step.
4. **`AtlasTicketingStrategy.cs`**: `IssueAsync` no longer throws when zero ticket numbers come back (that's now the expected/normal "pending" outcome, not an error); added `CheckPendingIssueAsync`, delegating to `AtlasTicketingService.CheckStatusAsync`. Genuine Atlas API failures (bad HTTP response, declined payment, etc.) still throw naturally from lower in the stack and are unaffected.
5. **`AirTicketingWorkflowService.cs`**:
   - The Atlas branch of `IssueAsync` now branches on `atlasIssue.TicketNumbers.Count == 0`: wallet-hold capture still happens immediately (Atlas's own payment already succeeded), but the booking is set to `AirTicketingStatus = AWAITING_EVIDENCE` (not `ISSUED`) when no tickets are back yet, with an INFO-level audit entry/notification — mirroring Travelport's existing pending-evidence handling instead of always marking `ISSUED`.
   - The "already `AWAITING_EVIDENCE`/recoverable `FAILED` → resume" dispatch now branches by provider: Atlas bookings route to a new `RefreshAtlasTicketEvidenceAsync` (calls `CheckPendingIssueAsync`, never re-pays); Travelport bookings keep using the existing `RefreshTicketEvidenceAsync` unchanged.
   - `RefreshAtlasTicketEvidenceAsync` mirrors `RefreshTicketEvidenceAsync`'s shape exactly, including the same `EvidencePendingWindow` (30-minute) escalation from `AWAITING_EVIDENCE` to a real `FAILED` state if Atlas never confirms the ticket.
6. **`AirTicketingDate` scheduling for Atlas**: verified, no change needed — `AtlasBookingController.cs` already sets `booking.AirTicketingDate = GetLocalToday()` before calling `IssueAsync`, identically to the Travelport flow, so the existing `GetDueBookingIdsAsync`/`AirTicketingWorker` (unchanged, provider-agnostic) already picks up pending Atlas bookings.
7. **API response shape**: found already implemented (apparently done in a separate pass since this plan was written) — both `AirBookingController.cs` and `AtlasBookingController.cs` already distinguish `ticketIssued` / `ticketingFailed` / "still in progress" and populate `AirBookingResponse.TicketingErrorDetail` accordingly. No controller changes were needed; the new pending/error outcomes from steps 1-5 flow straight into this existing logic correctly (a pending Atlas or Travelport booking now returns `WorkflowStatus = "AWAITING_EVIDENCE"`, which the controllers' existing `else` branch already renders as "still in progress," not success or failure).
8. Verified with `dotnet build` — clean, 0 warnings/errors. Confirmed via repo-wide grep that no leftover references to the removed retry constants/methods remain, and that `AtlasTicketingStrategy` is the only `IAirTicketingStrategy` implementer (so the new interface method didn't break anything else).

## Status
**Implemented.** Both providers' synchronous booking-confirmation path is now a single attempt (Atlas: pay once + one status check; Travelport: one ticketing call + one evidence check), with "no tickets yet, no error" landing in the existing `AWAITING_EVIDENCE` state instead of blocking inline, and the existing `AirTicketingWorker` background loop (unchanged) resolving it afterward — for Atlas via a new status-only recheck that never resubmits payment. Manual end-to-end verification against sandbox/live providers (per the Verification section above) is still recommended before relying on this in production.
